# 5. エラー処理・再試行・フォールバックの三層構造

## 三層の責務分離

同じ「失敗」でも回復手段を3つの独立した層に分ける:

| 層 | 手段 | 対象 |
|---|---|---|
| クライアント再試行 | 同じ要求を固定遅延で再送(既定: 最大2回、1.2秒間隔) | 一時的な HTTP/ネットワーク障害 |
| プロバイダー切替 | 同じプロンプトを代替 LLM プロバイダーへ | 一次プロバイダーの一時障害(rate limit、5xx、timeout、クレジット系) |
| ローカルフォールバック | アプリが契約形状を満たす固定出力を生成 | parse 不能・スキーマ破壊など出力品質の問題 |

層ごとに判定条件が異なることが重要: **出力品質の問題(malformed JSON、schema mismatch)はプロバイダーを切り替えても直らない**ので切替対象外。逆にプロバイダー障害はローカル固定文では正しく代替できないので、切替で対処する。

## エラー分類の原則

1. **Abort(ユーザーキャンセル)は最優先で除外**。どの層でも再試行・切替・フォールバックせず、そのまま伝播する。
2. **ハードエラーは絶対に握りつぶさない**: 認証失敗(401/403)、課金・クレジット不足(402)、モデル不存在は、ローカルフォールバックに変換せず利用者へ明示する。課金失敗を「自動復旧した成功」に見せると運用原因が隠れる。
3. 再試行可否は deny-list(認証・課金・モデル不存在・恒久エラー)を先に評価し、次に allow-list(timeout、5xx、rate limit、network、invalid JSON)。**未知エラーは再試行可能に倒す**(一時障害の取りこぼし防止)。
4. リトライ中の attempt 数・上限・最後のエラーは状態に記録し、UI が進行を可視化できるようにする。再試行を経て成功したら autoRecovered の印を残す。

## パース失敗からの回復手順

```
生応答
 → サイズ上限検査(超過なら retry せず直接ローカルフォールバック)
 → JSON 抽出・parse
 → 失敗なら圧縮リトライプロンプトを1回だけ送る
 → それでも失敗ならローカルフォールバック
```

フォールバックで完了した結果には **fallbackUsed / autoRecovered のフラグを必ず付け**、通常成功と区別できるようにする。監査(continuity)のフォールバックは「問題なし」の固定文になるため、実監査と混同させない表示が必要。

## ローカルフォールバックの設計

- 全エージェントに対し、**契約形状(スキーマ)を満たす言語別の固定出力**を用意する。パイプラインを止めないための応急値であり、品質は保証しない。
- 章構成のフォールバックは特別扱い: 固定文ではなく**スケルトンを再利用**して構造を守る。既存の part/章 ID・番号・lengthPlan を保持し、章位置比(序盤/中盤/山場/結末)から役割別の title/purpose シードを生成する。ユーザーはこれを編集してから承認できる。
- 章構成エージェントの再試行可能な失敗は、例外を外へ出さずフォールバック構成を適用してから承認待ちへ進める(計画段を途中破綻させない)。

## タイムアウトの階層

壁時計タイムアウトを層ごとに独立して設定する(参考値): エージェント全体 45秒、章構成の LLM 呼び出し 40秒、章生成 45秒、JSON parse 5秒。タイムアウトの caller signal と timer signal はリンクさせ、停止操作がネットワーク要求まで到達するようにする。

## エラーメッセージの契約

- **サニタイズ**: API キー形式・Bearer トークン・長い hex を [redacted] に置換し、長さ上限で切ってから表示する。
- **具体的な対処を含める**: 402/トークン超過なら「章長を減らす・クレジット追加・安価なモデル」、timeout なら「構成の簡素化・章長の縮小」を案内する。エラー種別ごとの整形は優先順位付きで1箇所に集約する。
- 生のエラーメッセージは整形済み文言とは別に保持し(lastRetryError、章の error)、原因調査で整形文だけに頼らない。

## 観測可能性

- エージェントごとの経過時間を段階別(LLM 呼び出し、parse、正規化、マージ)にログし、ボトルネックを分解できるようにする。
- 章生成順、プロンプトサイズ(文字数・推定トークン)をログする。
- parse 失敗時は生応答の**長さと先頭数百文字だけ**をログする(全文を書かない — コストと漏えい面の抑制)。
- provider 切替・構造フォールバックはプロジェクト状態にフラグを残し、「通常応答」と「救済経路」を後から区別できるようにする。
