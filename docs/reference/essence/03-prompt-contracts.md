# 3. プロンプト構築と構造化出力の契約

## 二重言語契約

**JSON のキーは常に英語、創作テキストの値はプロジェクト言語**。この分離により、日本語プロジェクトでもマージ処理が固定キーを機械的に読める。全プロンプトに共通 JSON 規則(valid JSON only、markdown・説明・コメント禁止、引用符と括弧を閉じる、キーは英語)を埋め込む。

プロンプトのスキーマは「返してほしい形の指示」であって実行時バリデータではない。強制はパース・正規化・検証の側で行う。

## コンテキストの累積と圧縮

後段エージェントには前段の成果を**圧縮ビュー**として渡す。生の全成果物を渡さない。

- **完了済みエージェント出力を Bible より優先**して読む。未完了・非オブジェクト出力は捨てて Bible の既存値へフォールバック。この優先順位を変えると同じプロジェクトでもプロンプトが変わり再現性が崩れる。
- フィールドごとに文字数上限を決めて切り詰める(例: concept 各項目 280字、人物 name 80字、plot 各区分 200字、twists 先頭3件×120字)。
- 配列は件数上限(人物は先頭8名、locations/symbols 各6件、tracker 先頭8件)。
- ユーザープロンプトの圧縮は **head/tail 方式**(先頭 N 字+末尾 M 字を marker で連結)。中間を落とす。
- 累積は共有オブジェクトの参照ではなく、毎回の圧縮ビュー再生成。

エージェント別のコンテキスト戦略:

- **editor(編集)**: 原稿が閾値以下なら全文、超えたら冒頭・末尾の抜粋+既往レポートの指摘上位数件。
- **continuity(監査)**: 原稿全文は渡さない。章要約+企画+人物+プロット+伏線 tracker+冒頭/中盤/結末の抜粋。
- **publisher**: 題名+企画+人物+プロット+結末抜粋+短い synopsis。

## プロンプト予算

エージェントごとに文字数上限(cap)を設け、送信直前に強制する。超過時は「コンテキスト部分から優先的に削り、marker を付ける」。トークン推定は文字数/4 程度の単純推定で足りる。プロンプトサイズは毎回ログする。

## 決定的スケルトン+穴埋め(章構成の核心パターン)

Chapter Architect は自由生成させない。**構造の数値はアプリが決め、LLM はテキストだけを埋める**:

1. アプリが構成設定から**スケルトン**を生成: part/章の number、role、lengthPlan を確定。role は3章なら Opening/Development/Resolution、それ以外は先頭 Opening・末尾 Resolution・中央 Climax・他 Development。
2. LLM への指示: number / role / lengthPlan を**変更禁止**、title / purpose / emotionalTurn / keyEvents / foreshadowing / styleGuide / tracker だけを返す。全文字列に短い上限(120字)、keyEvents 最大2、foreshadowing 最大1、tracker 最大3。
3. 受信後、モデル出力をスケルトンにマージ(スケルトンの number / role / lengthPlan を保護)。空 title/purpose はスケルトン値→決定的既定文で埋める。
4. **構造検証**: part数、章数、正で一意な章番号、title、purpose、正の目標長を検査。失敗なら retry → それでも駄目ならフォールバック構成(→ 05章)。

このパターンにより「章数が合わない」「長さ計画が消える」系の構造破壊をモデルに起こさせない。

## JSON 抽出

モデルは指示に反して余計なテキストを付けることがある前提で受信側を作る:

1. コードフェンス(```json)を剥がす。
2. 全体を JSON parse。
3. 失敗したら最初の object/array を括弧バランス走査で抽出(文字列内の quote / escape / brace を追跡し、説明文中の brace で切らない)。
4. 見つからない/閉じていない場合は明示的なエラー。

生応答にはサイズ上限を設け(通常用と、構造出力用のより厳しい上限)、超過は retry せず直接フォールバックへ送る。JSON parse 自体にもタイムアウトを付ける。

## リトライプロンプト

初回 parse 失敗時の再試行は、**同じプロンプトの再送ではなく圧縮版**を送る:

- 共通規則を再掲し「compact」を明示。
- ユーザープロンプトは大幅短縮(500字程度)。全プロジェクトを含めない。
- エージェント別に初回より厳しい上限(例: concept は JSON 全体700字未満、editor 各配列4件、publisher titleIdeas 3件)。

「初回は表現力、リトライは復旧確率」を優先する非対称設計。

## 補助契約(拡張・改稿)

- **章の拡張(expand)**: 現在長と目標長をプロンプトに埋め、「前提を変えない・要約しない・場面/会話/感覚描写/内的葛藤/転換を追加する・連続性を維持する」と指示。返却は draft+expansionSummary のみ。
- **計画の改稿(plan revise)**: ユーザー指示+圧縮コンテキストから partial patch+explanation+structureChanged を返す。変更不要のキーは omit。構造変更が必要な場合を除き parts/chapters を patch に含めない。structureChanged なら全章に needsRevision を付けて影響を追跡する。
- **章の改稿(chapter revise)**: 章番号+改稿本文+改稿要約を返す。
